## Подбор вина - Streamlit-приложение

Приложение оценивает вероятность того, что вино относится к классу
«хорошее», и рекомендует его, если вероятность не меньше выбранного порога.

### Требования

Для запуска используйте Python 3.13. Файл `model.joblib` сохранён с использованием scikit-learn 1.6.1, эта же версия указана в `requirements.txt`. При создании приложения в Streamlit Community Cloud выберите Python 3.13 в **Advanced settings**.
### Локальный запуск

Откройте терминал в папке, где лежит `app.py`, и выполните:

```bash
python -m pip install -r requirements.txt
python -m streamlit run app.py
```

После запуска откройте адрес, который Streamlit покажет в терминале (у меня он открывался даже сам).

### Файлы

- `app.py` - код приложения
- `model.joblib` - обученный пайплайн `StandardScaler` и
  `LogisticRegression` - модель в приложении не обучается заново
- `config.json` - порог по умолчанию
- `test.csv` - тестовые данные для вкладки «Модельные метрики» и
  диапазонов полей ввода
- `requirements.txt` - версии библиотек

### Ответ на вопрос, почему используются два вида кэша

Streamlit заново выполняет app.py при каждом действии пользователя, в том числе при изменении порога, но модель при этом 
не меняется. st.cache_resource загружает её через joblib.load один раз и затем возвращает тот же объект при следующих 
запусках скрипта. Это хорошо подходит для обученного пайплайна, так как его нужно многократно использовать для предсказаний, 
не создавая копию модели при каждом запуске.

test.csv и предсказанные вероятности это результаты чтения и вычислений. Для них мы уже используем st.cache_data. 
При одинаковых входных данных функция не читает снова CSV и не вызывает опять predict_proba, а берёт сохранённый результат. 
стримлит уже возвращает отдельную копию этих данных, поэтому изменение полученной таблицы или массива не испортит значение в кэше.
Порог не передаётся в функцию расчёта вероятностей: изменение порога меняет только метки классов, матрицу ошибок и метрики.

Если же убрать st.cache_resource и вызывать joblib.load напрямую, то каждое движение ползунка заставит приложение снова 
читать файл нашей модели с диска, восстанавливать пайплайн и создавать новый объект. Ответы модели останутся, конечно, 
такими же, но приложение будет работать намного медленнее. Кэшировать саму модель через st.cache_data для этого задания 
нельзя, так как он рассчитан на сериализуемые результаты и выдаёт копии, тогда как для модели требуется повторное использование 
одного загруженного объекта.
